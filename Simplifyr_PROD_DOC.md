1. Executive Summary
Simplifyr is an enterprise-grade Universal Log Pre-processing Framework (ULPF) designed to ingest, understand, normalize, standardize, and route heterogeneous logs and events generated by perimeter network devices.
The problem statement calls for a Universal Log Pre-processing Framework (ULPF). Simplifyr is our implementation of that framework.
Simplifyr is designed to handle events from different:
•	Vendors
•	Products
•	Software versions
•	Event types
•	Input formats
•	Field structures
•	Technologies
while preserving the complete original event data.
The central product philosophy is:
Configure once. Run continuously. Intervene only when necessary.
Simplifyr should not be a collection of manually maintained vendor-specific parsers. Instead, it should be a configuration- and knowledge-driven preprocessing platform in which vendor definitions, event structures, versions, mappings, and output profiles are represented as versioned knowledge/configuration.
The platform should support:
•	Real-time event ingestion
•	File-based ingestion for onboarding, testing and replay
•	Syslog, JSON, XML, CSV, CEF, LEEF and proprietary formats
•	Multiple vendors and products
•	Multiple software versions
•	User-defined output representations
•	Common output presets
•	Custom output schemas
•	Lossless raw-event preservation
•	Event provenance and traceability
•	Automatic schema/format drift detection
•	AI-assisted interpretation of unknown events
•	Human-in-the-loop approval
•	Version-aware onboarding
•	Air-gapped deployment
•	Containerized deployment
•	Horizontal scaling
•	SIEM and data-lake integration
•	AI/ML-ready outputs
The initial implementation focuses on perimeter network device-generated events, while the underlying architecture is intentionally designed to support additional event sources in the future.

2. Terminology: ULPF vs. Simplifyr
This distinction is fundamental to the product.
2.1 What is ULPF?
ULPF stands for Universal Log Pre-processing Framework.
It describes the framework capability required by the problem statement:
A framework capable of ingesting heterogeneous logs/events, parsing them, preserving the original data, normalizing their meaning, and producing standardized representations suitable for analytics and downstream cybersecurity platforms.
ULPF is therefore a concept/category/framework, not our product name.

Simplifyr is the product we are building.
Simplifyr implements the ULPF concept through:

3. Problem Statement
Enterprise environments generate enormous quantities of logs and events from devices and software with inconsistent structures.
For example, different firewall vendors may represent essentially the same event as:
src=10.10.1.5 dst=8.8.8.8 act=deny proto=tcp
or:
{
  "sourceAddress": "10.10.1.5",
  "destinationAddress": "8.8.8.8",
  "action": "DENY",
  "protocol": "TCP"
}
or:
<134>device=FW01 srcip=10.10.1.5 dstip=8.8.8.8 action=drop protocol=6
A human can recognize that these events represent similar concepts.
Enterprise systems cannot reliably assume that semantic equivalence without preprocessing.
This creates several challenges:
1.	Vendor-specific parser development.
2.	Large numbers of normalization rules.
3.	Difficult onboarding of new sources.
4.	Parser maintenance after software/firmware changes.
5.	Loss of information during normalization.
6.	Difficulty tracing normalized data back to its source.
7.	Inconsistent representations across security systems.
8.	High operational effort.
9.	Fragile processing pipelines.
10.	Difficulty scaling preprocessing across large environments.
Simplifyr addresses this preprocessing problem by implementing the ULPF architecture as an adaptive, lossless, knowledge-driven platform.

4. Product Vision
Simplifyr should eventually behave like infrastructure that an organization installs, configures, and then largely leaves alone.
The desired experience is analogous to a wall clock:
Initial configuration
        ↓
Connect event sources
        ↓
Define desired representation
        ↓
Simplifyr learns mappings
        ↓
Simplifyr runs continuously
        ↓
Known events processed automatically
        ↓
Only meaningful changes require human attention
The organization should not need to manually maintain parsers whenever a vendor changes its event structure.
Instead:
Environment changes
        ↓
Simplifyr detects change
        ↓
AI investigates
        ↓
Human validates when necessary
        ↓
Knowledge/configuration is updated
        ↓
Processing resumes
This leads to two fundamentally different operational planes:
Configuration & Intelligence Plane
Human interaction occurs here.
Runtime Processing Plane
High-volume deterministic processing occurs here.

5. Core Product Principles
5.1 Universal does not mean one universal output
Simplifyr should not force every organization into one rigid output schema.
Instead:
Vendor A ──┐
Vendor B ──┤
Vendor C ──┼──→ Simplifyr semantic understanding
Vendor D ──┤                │
Vendor E ──┘                ▼
                     Desired output
Users may select:
•	Security Operations preset
•	Network Operations preset
•	SIEM preset
•	Analytics preset
•	Machine Learning preset
•	General normalized event preset
•	Custom output schema
Presets accelerate onboarding.
They do not constrain the platform.
________________________________________
5.2 Universal means universal processing
Simplifyr should abstract away:
•	Vendor
•	Product
•	Version
•	Input format
•	Event type
•	Field naming
•	Encoding differences
The processing engine should operate primarily on semantic meaning, rather than hard-coded vendor-specific application logic.
________________________________________
5.3 Lossless by design
Normalization must never mean destruction of source information.
Every processed event should retain, directly or through references:
1.	Original raw event.
2.	Parsed representation.
3.	Normalized semantic representation.
4.	Final output representation.
5.	Provenance.
6.	Source metadata.
7.	Mapping/configuration version.
8.	Processing version.
9.	Event identifier.
Conceptually:
                         Original Event
                              │
             ┌────────────────┴────────────────┐
             │                                 │
             ▼                                 ▼
      Immutable Raw Storage               Processing
                                               │
                                               ▼
                                           Parsing
                                               │
                                               ▼
                                    Semantic Interpretation
                                               │
                                               ▼
                                          Normalization
                                               │
                                               ▼
                                        Output Profile
                                               │
                                               ▼
                                     Standardized Output
The original event remains available for:
•	Forensics
•	Compliance
•	Debugging
•	Reprocessing
•	Parser/mapping improvement
•	Auditability
________________________________________
5.4 Configuration over code
Adding a new vendor should ideally mean:
Add knowledge/configuration
rather than:
Modify source code
      ↓
Compile
      ↓
Test
      ↓
Redeploy
Vendor mappings, versions, event definitions and output profiles should therefore be represented as versioned configuration/knowledge.
________________________________________
5.5 Human-in-the-loop, not human-in-the-middle
Humans should not be required for every event.
Known events:
Known event
    ↓
Automatic processing
Unknown or ambiguous events:
Unknown event
    ↓
AI analysis
    ↓
Human validation
    ↓
Knowledge update
    ↓
Automatic processing
The human should intervene only when the system lacks sufficient confidence or when organizational policy requires approval.
________________________________________
5.6 Fail safely
Simplifyr should never silently invent a meaning for an event when confidence is insufficient.
Unknown events should be:
Received
   ↓
Identified as unknown
   ↓
Preserved
   ↓
Quarantined
   ↓
AI analysis
   ↓
Human approval
   ↓
Knowledge updated
   ↓
Reprocessed
An unknown event must never bring down the entire processing pipeline.
________________________________________
5.7 Runtime should be deterministic
AI should not sit on the critical path of every event.
Normal processing:
Event
 ↓
Source identification
 ↓
Known mapping lookup
 ↓
Deterministic parsing
 ↓
Normalization
 ↓
Output transformation
 ↓
Output
AI should primarily assist with:
•	Initial onboarding
•	Unknown sources
•	Unknown event structures
•	Schema drift
•	Version detection
•	Mapping suggestions
•	Event classification
•	Configuration assistance
This separation is essential for enterprise performance, reliability and predictability.

14. Mapping Definition
A mapping describes how source-specific fields correspond to semantic fields.
Example:
{
  "input_field": "srcip",
  "semantic_field": "source.ip",
  "transformation": "identity",
  "confidence": 1.0
}
A transformation mapping could be:
{
  "input_field": "act",
  "semantic_field": "network.action",
  "transformation": {
    "DENY": "BLOCKED",
    "DROP": "BLOCKED",
    "ALLOW": "ALLOWED"
  }
}
Mappings should be versioned and auditable.

22. Unknown Event Handling
Suppose a known firewall previously emitted:
src=10.1.1.5 dst=8.8.8.8 action=deny
and after a software update emits:
source=10.1.1.5 destination=8.8.8.8 decision=drop
Simplifyr should detect:
Known source
+
Known event family
+
Unexpected structure
Rather than treating this as a system failure, Simplifyr creates a drift event.

46. Quarantine vs. Dead Letter Queue
These should be different concepts.
Quarantine
The event may be valid, but Simplifyr does not currently understand it.
Unknown → Quarantine → AI/Human → Reprocess
Dead Letter Queue
The event could not be processed because of an error or malformed input.
Processing error → DLQ
Raw Storage
Regardless of processing outcome, the original event should be preserved according to configured retention policy.

73. The Most Important Architectural Insight
Vendor knowledge is data. Processing logic is software.
For example:
Processing logic:
"How do I execute a mapping?"

Knowledge:
"Vendor X v2 field `srcip` means source IP."
If Vendor X changes:
Knowledge changes.
The core processing engine does not.
This is the foundation of Simplifyr's scalability and extensibility.

                    AI
                     │

             Knowledge Registry
                     │
                     ▼
          Deterministic Runtime
                     │
                     ▼
                   Events

The latter would be expensive, slower, less predictable and more difficult to validate at enterprise scale.
